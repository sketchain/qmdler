# qmdler

QQ 音乐歌单批量下载器。**一个核心 + 一个服务 + 两个前端**：WebUI 与 TUI 都是纯客户端，
通过 HTTP/WebSocket 连同一个后端，任一端的暂停/取消对另一端立即可见。

> ⚠️ 本工具仅供**个人学习与备份自有权益内容**使用。请勿用于任何形式的分发、传播或商业用途，
> 由使用者自行承担因使用本工具产生的一切责任。

## 特性

- **五种登录方式**：QQ 扫码 / 微信扫码 / QQ 音乐 APP 扫码（MQTT 长连接实时推送）/ 手机号短信 / 直接导入 Credential
- **八种歌单来源**：自建歌单、收藏歌单、我喜欢、歌单 ID 或分享链接、专辑、歌手全部作品、搜索结果、手动 mid 列表
- **音质优先级链**：拖拽排序，逐档尝试，实际拿到的档位低于首选时明确标注「已降级」
- **四层试听检测**：`purl` 前缀 → `size_try` 交叉验证 → Content-Length 比对 → 落盘后时长校验。
  检出的试听片段记为独立状态 `trial`，**绝不混进「成功」**
- **风控友好**：严格串行、一首一首取链下载，默认每首之间间隔 180 秒（支持随机区间），
  元数据请求走独立的轻量限速
- **断点续传**：状态落 SQLite，`.part` 临时文件 + HTTP Range，重启后从断点继续
- **主动凭证刷新**：后台定时任务提前刷新，不等到请求失败才补救
- **完整元数据**：FLAC / MP3 / M4A / OGG 四套 tag 写法，QRC 逐字歌词转增强 LRC，六档封面
- **响应式**：WebUI 桌面三栏、手机单栏 + 底部标签栏 + 卡片列表；TUI 在 40 / 80 / 120 列都可用

## 安装

需要 **Python ≥ 3.10**。

```bash
git clone https://github.com/sketchain/qmdler
cd qmdler
pip install .
```

开发安装（含测试与静态检查工具）：

```bash
pip install -e ".[dev]"
```

WebUI 的前端依赖（Vue 3、SortableJS）**已随包分发**，不需要 Node，也不会去请求任何 CDN。

## 快速开始

```bash
# 启动 WebUI（同时也是 TUI 连接的后端）
qmdler web
# → http://127.0.0.1:8770

# 启动 TUI（检测不到后端时会自动拉起一个本地服务）
qmdler tui

# 终端扫码登录（同时给出图片地址、落盘路径、字符画）
qmdler login --method qq

# 纯 CLI 无人值守
qmdler download --playlist 7392570702

# 诊断一首歌：跳过间隔，打印四层校验每层的实际判定值
qmdler single 003w2xz20QlUZt
```

三个入口共用同一份配置、同一个数据库、同一套下载逻辑。

## 登录

打开 WebUI 左侧的「选择登录方式」，或在 TUI 里按 <kbd>L</kbd>。

| 方式 | 说明 |
|------|------|
| **QQ 扫码** | 用手机 QQ 扫 |
| **微信扫码** | 用微信扫 |
| **APP 扫码** | 用 QQ 音乐 APP 扫，状态经 MQTT 长连接实时推送 |
| **手机验证码** | 可能要求先完成人机验证（会给出链接），也可能触发频率限制 |
| **导入 Credential** | 粘贴 `musicid` / `musickey`，或指定一个 JSON 文件路径 |

### 二维码的三条出口

对着终端字符画扫不方便，所以每次扫码都同时给出三条路，优先级从高到低：

1. **HTTP 图片端点（首选）**：`GET /api/auth/qrcode.png`，直接返回原始图片字节，
   `Content-Type` 取自 `QR.mimetype`（QQ 是 PNG，微信是 JPEG）。TUI 与 `qmdler login`
   会把**完整可访问地址**打印出来，包含实际监听的 IP:端口，以及本机的局域网 IP —— 
   手机连同一个网就能直接打开。不带 `session_id` 时返回最近一次会话的二维码。
2. **落盘文件**：调 `QR.save()` 存到 `$XDG_STATE_HOME/qmdler/qrcode/`，绝对路径一并打印。
3. **载荷文本（仅诊断）**：`qmdler login --diagnose` 会用 `zxing-cpp` 解出二维码里的
   URL 并打印，你可以自己转成更好扫的形式。**`zxing-cpp` 只在 dev 依赖里，运行时代码
   不依赖它**，没装就打一行安装提示，不影响登录。

字符画本身要过两道自检才会画出来 —— 还原出的模块数必须是 `21+4n`（QR version 1~40 的
合法边长），左上/右上/左下三个角必须匹配 7×7 定位图案。**任一不过就不画，只给上面三条路**，
绝不输出一张可能扫不出来的图。中心 logo 照原样画，QR 纠错会兜住。

字符画约需 45 列宽（半块字符纵向已是 1:1，没有再压缩的余地）；终端更窄时直接给地址。

**关于凭证持久化**

凭证保存在 `$XDG_CONFIG_HOME/qmdler/credential.json`，权限 `600`，字段是完整的 16 个
（不只是 `musicid` / `musickey`）—— 微信登录刷新要用 `openid` / `unionid` / `refresh_token`，
QQ 登录要用 `openid` / `access_token` / `expired_at`，少存任何一个下次都刷不动。

设备信息保存在 `device.json`，**必须持久化**。丢了它设备指纹每次重启都变，
等同于频繁换设备登录，极易触发风控 —— Docker 部署时一定要挂载 `/config`。

**导入凭证的一个限制**：只粘贴 `musicid` + `musickey` 时，凭证里没有 `encrypt_uin`（euin）。
「我喜欢」「收藏的歌单」和账号信息这三个接口需要 euin，会不可用（UI 上会提示）。
带上 `refresh_token` 时程序会自动刷一次换取完整凭证；否则请改用扫码登录。

## 使用

### WebUI

桌面宽屏是三栏布局：左侧歌单来源 / 中间曲目表 / 右侧任务面板。
窄屏（< 768px）自动折叠为单栏 + 底部标签栏，曲目表改为卡片列表。
可以「添加到主屏幕」当 PWA 用。

1. 左栏选一个来源 → 拉取曲目
2. 中栏勾选要下的歌（支持全选 / 反选 / 关键词过滤）→ 建任务
3. 右栏点「开始」，进度、倒计时、日志实时推送

### TUI

| 键 | 作用 | | 键 | 作用 |
|---|---|---|---|---|
| <kbd>L</kbd> | 登录 | | <kbd>G</kbd> | 开始 |
| <kbd>S</kbd> | 设置 | | <kbd>P</kbd> | 暂停 |

侧栏改用 <kbd>F1</kbd>/<kbd>F3</kbd> 全屏切换，不会横向滚动。

### 诊断模式

```bash
qmdler single 003w2xz20QlUZt            # 人读版
qmdler single 003w2xz20QlUZt --json     # JSON，方便贴出来
qmdler single 003w2xz20QlUZt --quality FLAC
```

只处理一首、跳过下载间隔，把四层校验**每一层的实际判定值**摊开：filename 前缀及其
取自哪个字段、请求档位编码、`size_*` 期望值、HEAD 还是 Range 分支拿到的 Content-Length
及差异百分比、逐个 CDN 节点的尝试结果、落盘后解出的时长 vs `interval`、试听窗口取自
`try_begin/try_end` 还是 `vi[4]/vi[5]`，最后给出 `success` / `trial` / `failed` 及理由。
另外会打印该曲目的 `sa` 原值（攒实测标定素材用）。

**输出里不会出现凭证、`musickey`、`vkey` 或完整 `purl`** —— `purl` 只打印最后一个路径段。
真漏了会被自检拦住并拒绝打印。

### CLI

```bash
qmdler download --playlist https://y.qq.com/n/ryqq/playlist/7392570702
qmdler download --album 000MkMni19ClKG --out /data/music
qmdler download --singer 0025NhlN2yWrP4 --limit 500
qmdler download --fav --interval 240
qmdler download --mids 003w2xz20QlUZt,004Z8Ihr0JIu5s

# 先看看会下什么，不实际下载
qmdler download --playlist 7392570702 --dry-run
```

退出码：`0` 全部成功，`1` 有失败项，`2` 参数错误。

## 配置

配置文件是 TOML，路径遵循 XDG：

| 用途 | 路径 |
|------|------|
| 配置 / 凭证 / 设备信息 | `$XDG_CONFIG_HOME/qmdler/`（默认 `~/.config/qmdler/`） |
| 数据库 | `$XDG_DATA_HOME/qmdler/qmdler.db` |
| 日志 | `$XDG_STATE_HOME/qmdler/qmdler.log` |

### 环境变量覆盖

所有配置项都能用环境变量覆盖，前缀 `QMDLER_`，嵌套用 `__` 分隔：

```bash
QMDLER_SERVER__PORT=8800
QMDLER_PATHS__SAVE_ROOT=/data/music
QMDLER_DOWNLOAD__INTERVAL_SECONDS=240
QMDLER_QUALITY__REJECT_TRIAL=true
```

优先级：内置默认 < TOML 文件 < 选中的预设 < 环境变量。

### 配置预设

内置两套，可一键切换：

- **无损归档** —— 母带优先、随机间隔、按 `歌手/专辑/曲序. 歌名` 归档、逐字歌词 + 大封面
- **手机随身版** —— 320k 优先、兜底最低可用档位、逐行歌词、只嵌 500px 封面

也可以把当前设置存成自己的预设。

### 文件名模板

占位符：`{歌名} {歌手} {专辑} {专辑艺术家} {作曲} {作词} {年份} {曲序} {碟号} {音质} {songmid} {歌单名}`

目录模板里的 `/` 就是目录层级。UI 里有实时预览，改一个字就刷新完整路径。

文件名按 **Windows 最严格标准**统一清洗（Linux/macOS 也照此执行，避免同步盘炸掉）：
非法字符 `\ / : * ? " < > |` 替换为全角、去掉控制字符与结尾的点和空格、
保留名（CON/PRN/AUX/NUL/COM1-9/LPT1-9）加下划线后缀、**按字节**（不是字符）截断到 120 字节。

现场版 / Remix 容易撞名，模板里加 `{songmid}` 可以彻底避免。

## 关于音质：请先读这一节

### 会员等级不是万能的

即使账号是超级会员，以下情况仍然拿不到源文件，与会员等级无关：

- **单曲付费 / 数字专辑**（`price_track > 0`、`pay_play == 1`）
- **该音质文件本就不存在**（`size_* == 0`）—— 母带 / 全景声只有部分曲目做过
- **地区版权限制或已下架**（`result == 104003`）
- **设备受限**（`result == 104013`）

> **`104003` 在有效凭证下依然会出现，且成因往往是出口 IP 的地区版权分区，与账号权益无关。**
> 实测（2026-08，已登录、`check_expired` 为假、`user.get_homepage` 正常）：同一凭证下
> 「起风了」全档 `result=0`，而「晴天」「海阔天空」「小城夏天」**所有档位**都是 `104003`。
> 三首失败的都是有明确地区分区的曲目。所以看到 `104003` 先别怀疑登录 ——
> 换一首无地区分区的曲目对照一下，就能区分「账号没权益」和「这个网络位置拿不到」。

所以选档要逐层筛：`status`（下架/待审核直接排除）→ `size_*`（为 0 排除）→
`pay`（**只作提示，不参与过滤**）→ `result` + 试听检测（最终裁决）。

### 为什么 `pay_down == 1` 也可能下得到

本项目走的是**播放**链路（`music.vkey.GetVkey` / `UrlGetVkey`），不是官方客户端的下载链路。
播放链路必须返回播放器能直接解码的流，所以拿到的是**明文音频**，可以直接写 tag、直接播放。
服务端按**播放权益**判定，因此 `pay_down == 1` 的曲目仍可能正常返回完整播放文件。

### 加密档位为什么不开放

传 `EncryptedSongFileType` 才会走 `GetEVkey`，产物是 `.mflac` / `.mgg` / `.mmp4` 加密文件
（就是官方客户端点「下载」后存到本地的形态）。**本项目不实现任何解密，不使用 `ekey`**，
所以加密档位默认不在 UI 中暴露 —— 下下来也放不了。

### 试听片段：本项目最重视的一件事

`result == 0` 且 `purl` 非空，**不代表**拿到的是完整源文件。服务端可能返回 30 秒试听片段，
也可能悄悄降级到更低档位。文件下下来了、tag 也写了、状态是成功，用户一年后才发现半个库是残的——
这是最危险的静默错误。所以做了四层校验：

1. **`purl` 里的 filename 前缀** vs 请求档位编码（请求 `F000` 回来 `RS02`/`O802` 即试听）
2. **`size_try` 绝对值比对** —— 该值是「试听片段有多大」的基准，**不是本曲正片的特征值**。
   实测 12 首只出现三个取值：`960887`（8 首，≈128kbps × 60s）、`481070`（1 首，约一半）、
   `0`（3 首，即该曲没有这项）。所以拿它跟正片大小做「交叉验证」量纲都不对；
   正确用法是文件大小落在 `size_try` ±2% 内直接判 `trial` —— 与 `interval` 无关、与档位无关。
   始终读响应里的字段，**不要硬编码 `960887`**；`size_try == 0` 时本层放行
3. **Content-Length** vs `size_*`（下载前先 HEAD 探，不合就不浪费 3 分钟）
4. **实际时长** vs `track.interval`（落盘后用 mutagen 读）

检出的记为 `trial` 状态，UI 上单独一栏，汇总报告里独立计数。
默认开启「拒绝试听文件」，检出即换下一档。

## 常见问题

**Q：为什么默认要等 3 分钟才下一首？**
批量高频请求是最典型的风控特征。间隔可以在设置里改，也支持随机区间（如 150~210 秒，更不容易被识别）。
等待时 UI 显示倒计时，可以点「立即下载下一首」跳过。

**Q：触发风控了怎么办？**
遇到 `RatelimitedError` 会立即暂停整个任务并明确提示，等你手动恢复。建议隔一段时间再试，
并把间隔调大、改成随机区间。不要缩短间隔硬刚。

**Q：能不能并发下载快一点？**
不能，这是有意为之。全局只允许一个任务在跑，任务内严格串行，一首一首取链下载。
批量取链会让 vkey 提前失效（几小时后半段全部失效），也是最典型的风控特征。

**Q：`.nac` 格式的歌没有 tag？**
`.nac` 是腾讯自研容器，mutagen 不支持。音频文件正常保留，只是跳过 tag 写入并在记录里标注。

**Q：歌词是乱码 / 加密的？**
不会。`get_lyric` 返回的 `lyric` / `trans` / `roma` 已由库自动解密，是明文。
如果你选了「原样保存 .qrc」，那存下来的就是带 XML 外壳的 QRC 原文，这是预期行为。

**Q：封面 404？**
六档尺寸（150/300/500/800/1200/1500）里高尺寸不一定存在，程序会自动降到下一档。
专辑和歌手都没有封面时留空，不影响下载。

**Q：重启后任务丢了？**
不会。状态在 SQLite 里，重启后未完成的任务可以继续，已成功的直接跳过。
判重依据是 **songmid + 目标音质**，不是文件名。

**Q：`.part` 文件是什么？能删吗？**
下载中的临时文件，完整校验通过后才改名成正式文件。启动时会自动清理无主的 `.part`
（数据库里没有对应「下载中」条目的残片），避免续传接到上上次的残片上。

**Q：WebUI 白屏？**
如果你在前面加了带 `script-src` 严格限制的反向代理 CSP，需要允许 `'unsafe-eval'`：
Vue 全局构建自带的运行时编译器依赖 `new Function`。自托管直连不受影响。

**Q：TUI 显示不下二维码 / 对着字符画不好扫？**
每次扫码都会同时给出图片 HTTP 地址（含局域网 IP，手机直接打开）和落盘文件路径，
见「[二维码的三条出口](#二维码的三条出口)」。字符画只是其中一条，且过不了自检就不画。

**Q：一直提示 CDN 403？**
正常。实测同一条链接在多数节点上都是 403，只有个别节点放行 —— 程序会自动换节点重试
同一条链接，不会为此重新取 vkey。`qmdler single` 里能看到逐个节点的尝试结果。

### 关于测试素材

- `tests/data/qr/` —— 两张**真实**登录二维码（取回两分钟即过期，不含账号信息）。
  用真图而不是自己生成的，是为了覆盖非整数的每模块像素数、JPEG 噪点、中心 logo
  这些真实形态。
- `tests/fixtures/api/` —— **真实 API 响应的脱敏快照，目前刻意空着**。
  引擎那批 mock 的结构是照着模型定义想出来的，能证明控制流对、证明不了「我们对响应的
  理解对」。往里塞自己编的 JSON 只是把凭空 mock 换个地方，所以宁可空着让契约测试整体 skip。
  填充方式见该目录 README，脱敏走 `scripts/redact_snapshot.py`（按键名抹敏感字段、
  保留结构与类型，落盘前自检有无残留）。

### 项目结构

```
src/qmdler/
├── core/       下载引擎、任务调度、元数据处理、文件名生成、持久化
├── server/     FastAPI，REST + WebSocket
├── web/        浏览器前端（Vue 3 全局构建，依赖已 vendored）
├── tui/        Textual 应用
└── cli.py      三个入口
```

**架构硬约束**：`core` 不 import `server` / `web` / `tui` 中任何内容。
两个前端都是纯客户端，各自不实现任何下载逻辑。

## 与上游库的已知差异

基于 `qqmusic-api-python==0.7.2` 实测。

### 官方文档已过期的地方

上游 docs 站是 mkdocstrings 渲染的 docstring，但 `tutorial/` 下的手写教程没跟上 0.7.x 的重构。
以下两处**文档里的写法在 0.7.2 中直接不存在**，照抄会 `AttributeError`：

| 官方文档 `tutorial/credential` 写的 | 0.7.2 实际情况 | 正确写法 |
|---|---|---|
| `await credential.refresh(client)` | `Credential` 上根本没有 `refresh` 方法；它是 `frozen=True` 的 pydantic 模型，只有 `is_expired()`，原地改也不可能 | `new = await client.login.refresh_credential(old)`，再把返回的**新对象**回写 `client.credential` |
| `client.user.get_euin(credential.musicid)` | `UserApi` 上没有 `get_euin`（`dir(UserApi)` 里查无此名） | euin 的唯一来源是登录响应里的 `encryptUin`，即 `credential.encrypt_uin` |

两处均已在 0.7.2 wheel、GitHub `main` 分支源码与运行时 `hasattr` 三重确认。

### 文档与源码都没写、本项目刻意不猜的地方

| 字段 | 情况 | 本项目的做法 |
|---|---|---|
| `Song.sa` | docstring 只说「64 位权益位掩码，标识 HQ/SQ/Hi-Res/Atmos/Master 权益及试听状态」，**具体哪一位是什么，源码、docs 站、GitHub main 全都没有** | 原值透传给 UI 展示、`--single` 里原样打印，**不参与任何选档或试听判断**。猜错的后果正好是最怕的两种：能下的歌被静默跳过，或试听被当成完整文件 |
| `Song.genre` 的 ID 映射 | 注释引用的「文档 5.3.1 映射表」在仓库和文档站里都不存在 | 不臆造映射表，`{流派}` 改走 `album.get_detail()` 返回的流派**文本**，按 `album_mid` 缓存；拿不到就留空 |

`sa` 若要启用，唯一可靠路径是实测标定（取若干组已知状态的曲目做按位交集/差集），
不是继续找文档。`qmdler single` 会打印 `sa` 原值，就是为了攒这批素材。

### 其它对不上的地方

| 声称 | 实际 |
|---|---|
| `get_song_urls` 超过 100 个 mid 抛 `ValueError` | 常量 `_GET_SONG_URLS_MAX_MID = 100` 定义了、docstring 也写了，但函数体里没有任何校验。本项目自行分批 |

### 实测发现（2026-08，未登录取试听档）

这几条不是文档问题，是只有真跑才会暴露的行为：

- **同一条 `purl` 在多数 CDN 节点上是 403 —— 这不是链接失效，也不是节点故障。**
  12 首不同的歌，逐节点实测：

  | 节点 | 放行 |
  |---|---|
  | `https://sjy6.stream.qqmusic.qq.com/` | 12 / 12 |
  | `http://sjy6.stream.qqmusic.qq.com/` | 10 / 12 |
  | `http://aqqmusic.tc.qq.com/` | 0 / 12 |
  | `https://aqqmusic.tc.qq.com/` | 0 / 12 |
  | `http://ws.stream.qqmusic.qq.com/` | 0 / 12 |
  | `http://ws6.stream.qqmusic.qq.com/` | 0 / 12 |

  排除其它解释的依据：keepalive 探针（`GetCdnDispatchResponse.test_file`）6/6 返回 200，
  排除节点故障；同一条 purl 在放行节点上能稳定下完并逐字节校验通过，排除 vkey 过期。

  **所以遇到 403 要换节点重试同一条 purl（零额外 API 请求），而不是重新取 vkey**
  —— 后者会把每首歌的接口请求数翻好几倍，正是最该避免的风控特征。
  这条结论无法从代码推导，已写进 `cdn.py` 的模块 docstring 和 `STALE_LINK_STATUSES`
  的定义处，避免以后有人顺手把 403 加回去。

- **放行节点在不同 purl 之间是稳定的**，更像客户端/出口 IP 维度的属性，而非
  (purl, node) 的一次性绑定：随机挑一个的首次命中率 30.6%，固定挑历史最优节点是 100%。
  因此节点偏好有价值，但实现上必须**可逆**——用「最近一次成功」+「自上次成功以来的
  连续拒绝数」排序，一次成功即清零，成功记录还会过期。而「这条 purl 被谁拒过」是
  per-purl 的，换歌即丢，不跨曲目累积。
- **放行的节点支持 HEAD**，直接 200 并给出准确 `Content-Length`；`Range: bytes=0-0` 退化分支
  也能正常读出 `Content-Range`。两条分支都验证过。
- **`file.try_begin/try_end` 与 `vi[4]/vi[5]` 会不一致，而且它们是并列候选而非主备。**
  实测某首歌 `file` 给 84346~142843ms（58.5s），`vi` 给 84346~114346ms（30s）。
  差距太大，不像取整误差，更像是不同档位各有各的试听区间。
  因此两个区间**全部记录**，第 4 层时长校验**逐个比对，命中任意一个即判 `trial`**——
  `file` 优先只用于展示与默认值，不作为判定时的排他选择。漏判 trial 正是这个项目最怕的方向。
- **`GetCdnDispatchResponse.test_file` 是一条完整带 `vkey`/`guid` 的 URL**，不是路径。
  做日志脱敏和响应快照时别漏了它。

### 实测发现（2026-08，已登录）

登录后重跑，上面那批未登录结论有一条被推翻、两条被补强：

- **`size_try` 取值高度离散，既不是常量也不是本曲正片的特征值。** 12 首实测只出现
  三个值：`960887`（8 首）、`481070`（1 首）、`0`（3 首）。960887 ≈ 128kbps × 60s，
  与上一轮实测 `RS02` 试听片段的 Content-Length 精确相等；481070 差不多是它的一半。
  所以它是「试听片段有多大」的**绝对基准** —— 用法见上文第 2 层，别硬编码，也别在
  `== 0` 时硬判。
- **`vi[5] - vi[4]` 恒为 30000ms，`file.try_end - try_begin` 因曲而异，且不总是更大。**
  12 首里 `file` 窗口从 20.5s 到 67.5s 不等，其中「海阔天空」的 25.5s **短于** `vi` 的 30s；
  另有曲目（`003SQTG94ALCxQ`）**根本没有 `vi` 窗口**。这坐实了两者是并列候选、
  不存在主备关系，任何一个都可能缺席。
- **`size_* > 0` 与「取链能成功」高度一致。** 用真实凭证对 8 首可播放的歌逐档探了
  105 个 `size_* > 0` 的档位，**无一取链失败**（`result` 全为 0）。反过来，`size_*` 为 0
  的档位（如这两首没做过母带的曲目请求 `MASTER`）稳定返回 `104003`。
  也就是说 `build_plan` 的 size 过滤已经承担了绝大部分选档工作，
  「链上有大小却取不到」的真实降级极其罕见 —— 罕见不等于不发生，记账仍然必须正确。
- **`104003` 与账号权益无关时的成因是出口 IP 的地区版权分区**，详见上文「会员等级不是万能的」。
  已排除请求参数的干扰：对受限曲目补齐 `song_type` 与 `media_mid` 重试，结果不变。
- **读不出时长时第 4 层等于没跑。** `.nac` 是腾讯自研容器，mutagen 读不出时长，
  `check_duration` 会因为 `actual_seconds <= 0` 直接放行 —— 看上去是「ok」，实际是
  这一层被跳过了。现在诊断输出把这种情况单独标成 `unverified`，普通运行也会打一条
  warning，避免「四层校验」在无声中变成三层。
